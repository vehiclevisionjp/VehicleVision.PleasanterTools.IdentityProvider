# リリース手順書

## バージョンの付け方

**セマンティックバージョニング（`メジャー.マイナー.パッチ`）を使う。**
タグは `v` を付けて `v1.2.3`。

| 上げるもの | いつ |
| --- | --- |
| メジャー | **後方互換を壊す変更。** IdP 自身の DB の互換が切れる、SAML / OIDC の連携先の設定が変わる、Pleasanter の DB の読み方が変わる |
| マイナー | 機能追加。互換は保つ |
| パッチ | 不具合修正のみ |

- **`1.0.0` 未満は互換を保証しない。** 第 1 弾のリリースまでは `0.x.y` を使う
- プレリリースは `v1.0.0-rc.1` のように付ける

> **Dealer 方式（`X.Y_Rev_YYYYMMDD`）を採らない理由。**
> あちらは特定顧客向けに同一系列を継続的に納品する製品で、日付が版の意味を持つ。
> **本製品はデュアルライセンス（AGPL ＋ 商用）で外部へも配布し得るため、
> 利用者が互換性を判断できる必要がある。** 日付では互換の有無が分からない。

### アセンブリのバージョン

`Directory.Build.props` の `VersionPrefix` を単一の情報源にする。
**各 `.csproj` に個別のバージョンを書かない。**

## リリースの手順

**`major` / `minor` / `patch` を選んで「リリース実行」ワークフローを回すだけ。**
`.github/workflows/release-run.yml` が採番からタグ push まで通し、
タグの push を受けて `release.yml` が GitHub Release を作る。

```mermaid
flowchart LR
    A["develop で開発"] --> B["リリース実行を dry-run"]
    B --> C["リリース実行（bump を選ぶ）"]
    C --> D["VersionPrefix を上げる PR → develop"]
    D --> E["develop → master の PR"]
    E --> F["master へ v タグ"]
    F --> G["GitHub Release 作成"]
```

1. **`develop` で対象の変更がすべて入っていることを確認する**
2. **dry-run を回して、出る版を確かめる**（下記「dry-run」）
3. **「リリース前の確認」の「人」の欄を済ませる**
4. **`develop` から「リリース実行」を回す**

```bash
# 2. まず dry-run（既定で dry_run=true）
gh workflow run release-run.yml --ref develop -f bump=minor

# 4. 実際に出す。acknowledge は「人」の確認を済ませた表明
gh workflow run release-run.yml --ref develop     -f bump=minor -f dry_run=false -f acknowledge=true
```

**ここから先は自動。** ワークフローは次を順に行う。

| 段 | すること |
| --- | --- |
| 採番 | 既存の最新 `v*` タグを起点に次の版を決める（`scripts/release-next-version.sh`） |
| 版上げ | `VersionPrefix` を上げる PR を `develop` へ出し、auto-merge で squash マージ |
| 取り込み | `develop` → `master` の PR を出し、auto-merge でマージ（**squash しない**） |
| タグ | `master` の該当コミットへ `vX.Y.Z` を付けて push |
| Release | ここから `release.yml`（`gh release create`） |

### 採番の決まり

| 上げるもの | 結果 |
| --- | --- |
| `major` | `1.4.2` → `2.0.0` |
| `minor` | `1.4.2` → `1.5.0` |
| `patch` | `1.4.2` → `1.4.3` |

- **起点は既存の最新 `v*` タグ。** 実際に出した版を起点にすれば重複しない。
  `VersionPrefix` を起点にすると、タグを付ける前に `VersionPrefix` だけ先に
  上げてあった場合に二重に上がる
- ⚠️ **起点に採るのは最終リリースのタグだけ**（`vX.Y.Z`）。
  プレリリースは起点にも採らず、この仕掛けでは発行しない
- ⚠️ **タグがまだ 1 つも無い初回は、`VersionPrefix` をそのまま出す版とし、
  `bump` の指定を無視する。** 起点が無いところで上げると、`0.1.0` を作ったのに
  `0.1.1` から始まる食い違いになる
- **`VersionPrefix` が起点のタグとも次の版とも一致しないときは止まる。**
  手で書き換えた形跡がある状態で進むと、配布物の中身とタグの表す版が食い違う

### ⚠️ 前提: `my-repo-automation-bot`（GitHub App）

**`GITHUB_TOKEN` では動かない。** `master-protection` は PR 必須＋必須ステータス
チェックで、**`GITHUB_TOKEN` の push / PR 作成では CI が起動しない**ため
（ワークフローの連鎖を防ぐ GitHub の仕様）、必須チェックが永久に pending になって
マージできない。

**Dealer と同じ GitHub App を使う**（`VehicleVision.Dealer` の `create-release-tag.yml` /
`create-release-pr.yml`）。`actions/create-github-app-token@v3` が毎回 installation token を
発行するので、**長期の PAT をリポジトリへ置かずに済む。**

| 置き場所 | 名前 | 中身 |
| --- | --- | --- |
| Repository **Variables** | `MY_REPO_AUTOMATION_BOT_CLIENT_ID` | App の **Client ID**（`Iv23li…`） |
| Repository **Secrets** | `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` | App の秘密鍵（PEM） |

- ⚠️ **入れるのは Client ID。App ID でも Object ID でもない。**
  App の Settings → General に Client ID が載っている。
  `actions/create-github-app-token` は `app-id` より `client-id` を推奨している
  （<https://github.com/actions/create-github-app-token>、2026-09-11 参照）
- ⚠️ **App 側の権限が Contents / Pull requests とも Read and write になっていること。**
  既定が Read-only のことがある。ブランチとタグの push に Contents、
  PR の作成と auto-merge の予約に Pull requests が要る
- **未設定のまま `dry_run=false` で回すと、PR も作らずに止まる。** 先に落とす作りにしてある

### ⚠️ 一気通貫の実行が途中で落ちたとき

**途中まで進んだ状態が残る。** よくあるのは「`VersionPrefix` は上がったがタグが無い」。

- **同じ入力で再実行してよい。** 既にあるブランチ・PR・タグは作り直さず引き継ぐ
    - `VersionPrefix` が既に次の版なら、版上げの PR は省かれる
    - `develop` の commit がすべて `master` に入っていれば、取り込みの PR は省かれる
      （`master` へは merge コミットで入るため、SHA は一致しない）
    - タグが既に push 済みなら、タグ付けは省かれる
- **必須チェックが落ちて止まったときは、直してから再実行する。**
  auto-merge の予約は残っているため、緑になった時点でマージされることもある
- ⚠️ **タグが push された後に気付いた問題は、次のパッチ版で直す。**
  `release-tag-protection` でタグは付け直せない

### 手でリリースするとき

ワークフローが使えない場合（App の設定が未了、GitHub Actions が落ちている）は
従来どおり手で行う。

1. **`VersionPrefix` を上げる PR を `develop` へ出す**
2. **`develop` → `master` の PR を出す。** base は `master`
3. 必須チェック通過後にマージする
4. **`master` の該当コミットへ `vX.Y.Z` のタグを付けて push する**
5. **GitHub Release ができる。** ここから先は `release.yml` が行う

### 機能追加が混ざった develop から、修正だけを先に出すとき

**一気通貫のワークフローは develop の全変更を出す。** 脆弱性の修正など、機能追加を含めずに
パッチだけ先に出したいときは、直前のタグから分岐して手で出す。

1. **直前のタグから枝を切り**、修正のコミットだけを `cherry-pick` して `VersionPrefix` を上げる
2. **base を `master` にした PR を出し**、必須チェックが通ったら **merge コミットでマージする**
3. `master` のマージコミットへ `vX.Y.Z` のタグを付けて push する（Release は自動で出る）
4. ⚠️ **develop の `VersionPrefix` を、出した版へ揃える PR を先に通す。**
   起点のタグと `VersionPrefix` が食い違うと、次の「リリース実行」が採番で止まる
5. ⚠️ **`master` を `develop` へ戻す PR を、merge コミットで通す。** 戻さないと、次の
   `develop` → `master` の PR が `VersionPrefix` の行で衝突して進まない。squash では系譜が繋がらない
    - 衝突するのは `Directory.Build.props` だけのはずなので、`develop` 側の値を採る

### タグを付けるとき

- **タグは `master` にだけ付ける。** `develop` へ付けない
    - Release ワークフローが `git merge-base --is-ancestor` で確かめ、
      含まれていなければ Release を作らずに落とす
- **タグを付け直さない。** `release-tag-protection` で削除・force push を禁止している。
  間違えたら次のパッチ版を出す

```bash
git switch master && git pull
git tag v0.2.0
git push origin v0.2.0
```

## Release ワークフロー

`.github/workflows/release.yml`。**`v*` タグの push で動く。**

```mermaid
flowchart LR
    A["v タグを push"] --> B["リリース検証"]
    B --> C["GitHub Release 作成"]
```

| ジョブ | すること |
| --- | --- |
| `リリース検証` | タグの形式・タグが `master` に含まれること・`VersionPrefix` との一致・ビルド・単体テスト・フロントエンド・`license-check.sh`・`notice-check.sh`・配置用 ZIP |
| `GitHub Release 作成` | 日本語の本文を組み立てて `gh release create`。配置用 ZIP、SHA-256、ライセンス 4 ファイルを添付 |

- **Release 本文は前回のタグからのコミット件名で組み立てる。**
  squash マージの運用なので、件名がそのまま PR のタイトル（日本語）になっている
    - `gh release create --generate-notes` は使わない。見出しが英語で入るため
    - ⚠️ **自動生成された本文には目を通すこと。** マイグレーションの適用手順など、
      コミット件名に出てこないものは入らない
- **プレリリース（`v1.0.0-rc.1`）は自動で prerelease 印が付く**
- **`4 RDBMS 結合テスト` はここでは回さない。** タグは `master` 上のコミットへ付ける
  決まりで、そのコミットは `master` への push 時点で `integration.yml` が検証済み

### dry-run

**リリース経路はリリース時にしか動かないため、壊れていても次のリリースまで気付けない。**
`release-run.yml` と `release.yml` の両方に `dry_run`（既定 `true`）がある。
**リリース作業に入る前に両方回すこと。**

```bash
# 出る版と前提の確認（PR もタグも作らない）
gh workflow run release-run.yml --ref develop -f bump=minor

# Release 経路そのものの確認（Release を作らず検証だけ）
gh workflow run release.yml -f dry_run=true
```

| ワークフロー | dry-run で見るもの | 省くもの |
| --- | --- | --- |
| `release-run.yml` | 採番結果・`VersionPrefix` の整合・`develop` の CI・App の設定の有無 | PR 作成、マージ、タグ push |
| `release.yml` | ビルド・単体テスト・フロントエンド・`license-check.sh`・`notice-check.sh`・配置用 ZIP | Release 作成、タグと `master` の包含関係 |

既存の `v*` タグが無い初回 Release 前は、`release.yml` は
`Directory.Build.props` の `VersionPrefix` を Release 候補として使う。

## リリース物に含めるもの

| 種別 | 内容 |
| --- | --- |
| ソース | GitHub が自動で付ける |
| 配置用 ZIP | `VehicleVision.PleasanterTools.IdentityProvider-X.Y.Z-portable.zip`。Azure Web App／IIS 共用。**`*.pdb` は含めない。** RID を指定しない発行なので `portable` と名乗る |
| チェックサム | 配置用 ZIP と同名の `.zip.sha256` |
| 変更内容 | Release 本文。**日本語** |
| ライセンス | `LICENSE` / `LICENSING.md` / `LICENSE-COMMERCIAL.md` / `NOTICE` |

配置用 ZIP の直下は、そのまま Web アプリの配置先になる。Release ワークフローは
次が含まれることを検査してから ZIP を作り、SHA-256 を再検査して Release へ渡す。

- サーバ DLLと IIS 用 `web.config`
- `wwwroot/index.html`
- `App_Data/Parameters/README.md`
- ライセンス 4 ファイル

**`NOTICE` の依存一覧が最新であることをリリース前に確認する。**
デュアルライセンスの前提（依存はすべて寛容ライセンス）が崩れていないかの確認でもある
（[`../LICENSING.md`](../LICENSING.md)）。

## リリース前の確認

| 確認項目 | 誰が |
| --- | --- |
| `dotnet build` が警告 0 で通る | Release ワークフロー（`TreatWarningsAsErrors=true`） |
| 単体テストが通る | Release ワークフロー |
| **4 RDBMS 結合テストが通る**（SQL Server / PostgreSQL / MySQL） | `integration.yml`（`master` への push 時） |
| `scripts/license-check.sh` が通る | Release ワークフロー |
| `NOTICE` の依存一覧が実際の依存と一致している | `scripts/notice-check.sh`（Release ワークフローと `dependency-audit.yml`） |
| 配置用 ZIP に DLL、画面、設定の説明、ライセンスが含まれ、SHA-256 が一致する | Release ワークフロー |
| **破壊的変更があればメジャーを上げている** | **人** |
| マイグレーションがある場合、**適用手順を Release 本文に書いている** | **人**（自動生成の本文へ追記する） |
| 依存のライセンスが寛容ライセンスのままか | **人**（[`../LICENSING.md`](../LICENSING.md)） |

**「人」の欄は機械で確かめられないもの。** ワークフローが緑でも確認は要る。
**`release-run.yml` を `dry_run=false` で回すときは `acknowledge=true` を明示する。**
この 3 つを済ませたという表明であり、省くと実行前に落ちる。

> **タグは付け直せない。** 検証はタグを push した後に走るので、
> 失敗したら次のパッチ版を出すことになる。
> **リリース作業に入る前に dry-run を回しておくこと。**
