# 非機能設計

セキュリティを中心に、**何をどう防いでいるか**と、それを**どこで確かめているか**を対にして書く。
**防いだつもりのものは、確かめていないものを書かない。** 確かめていないものは「未確認」と明記する。

## 1. 脅威と対策

| 脅威 | 対策 | 確かめている所 |
| --- | --- | --- |
| パスワードの総当たり | ログイン ID ごとに失敗を数えて締め出す（DB。複数インスタンスで共有）。IP ごとのレート制限 | `LoginEndToEndTests`（締め出し・存在しない ID も同じ・成功で消える・レート制限）、`StoreTests`（並列に失敗を数える） |
| ログイン ID の実在の推測 | 誤りと不存在で同じ応答・同じ時間（ダミーのハッシュ計算）。存在しない ID も同じ回数で締め出す。通せない理由はパスワードが合ったあとにだけ返す | `LoginEndToEndTests`、`AuthenticationServiceTests` |
| TOTP の総当たり | パスワードと同じ鍵で数える。パスワードを知っていても 5 回まで | `LoginEndToEndTests.コードの総当たり…`、`AuthenticationServiceTests` |
| 盗み見られた TOTP の再利用 | 使った枠を覚え、同じか古い枠を断る（条件付き更新で、並列でも 1 回） | `LoginEndToEndTests.使用済みのコード…`、`StoreTests`（並列） |
| TOTP の共有鍵・パスワードのハッシュの漏えい | どの応答・ログ・監査ログにも出さない。クレームの元に含めない | `UserClaimsTests`、`OidcEndToEndTests`、`AdminEndToEndTests`（応答の本文を検査） |
| オープンリダイレクト（ログイン後の戻り先） | 同じオリジンの絶対パスだけ（`//` `\` スキーム付き・制御文字は弾く） | `ReturnUrlTests`、`LoginEndToEndTests.戻り先に外部の URL は使えない` |
| ログインフォームの CSRF | 二重送信 cookie + `Origin` / `Referer` の一致 | `CsrfGuardTests`、`LoginEndToEndTests` |
| 管理 API の CSRF | `X-IdP-Admin: 1` ヘッダ（プリフライトが要る）+ `Origin` の一致 | `AdminEndToEndTests.更新系は CSRF 用のヘッダとオリジンが要る` |
| セッション固定化 | ログインのたびに新しい ID を発行し、以前のセッションを閉じる | `LoginEndToEndTests.ログインのたびに新しいセッション ID を発行する` |
| セッション cookie の盗用・改ざん | `HttpOnly`・`SameSite=Lax`・`Secure`（https のとき）。署名付き（HMAC）。本体は DB にあり、失効できる | `CookieSignerTests`、`AdminEndToEndTests`（失効） |
| クリックジャッキング | `frame-ancestors 'none'` | `LoginEndToEndTests.ログイン画面は安全なヘッダ付き…` |
| XSS | 値は必ずエンコード。インラインのスクリプト・スタイルを使わない（CSP `script-src 'self'`）。SAML の自動送信だけ、別ファイルの JS と、ACS のオリジンだけを許す `form-action` | `HtmlPagesTests`、`SamlEndToEndTests`（CSP） |
| 認可コードの盗用・再利用 | PKCE（S256）。1 度きり（条件付き更新）。再利用で系統を全て失効。短命（60 秒）。クライアントと `redirect_uri` の一致 | `OidcEndToEndTests`、`StoreTests`（並列） |
| リフレッシュトークンの盗用 | 使うたびに替える。古いものが来たら系統を失効。ログアウト・セッション失効で止まる | `OidcEndToEndTests` |
| リダイレクト URI のすり替え | 完全一致。確定するまでエラーをリダイレクト先へ返さない | `OidcEndToEndTests.登録されていないリダイレクト URI…` |
| 認可応答のすり替え（mix-up） | 応答に `iss` を付ける（RFC 9207） | `OidcEndToEndTests` |
| JWT のアルゴリズムのすり替え（`none`・公開鍵を HMAC の秘密に） | RS256 だけを受ける | `OidcTokenServiceTests` |
| アクセストークンと ID トークンの取り違え | `typ`（`at+jwt`）と宛先（`aud`）を見る | `OidcTokenServiceTests` |
| 他所のオリジンのスクリプトからのトークン・UserInfo の呼び出し（CORS） | 登録されたクライアントのリダイレクト URI のオリジンだけに許す。資格情報（cookie）は伴わせない。ログイン・管理 API・SAML には CORS を付けない | `OidcEndToEndTests.ブラウザ上の RP のために CORS を付けるが…` |
| 失効したセッションのトークンの使用 | UserInfo はセッションの失効を確かめる | `OidcEndToEndTests.ログアウトすると…` |
| SAML の要求の偽造・改ざん | 署名付きの要求を、登録した証明書で検証（`SignAuthnRequest` を明示して立てる）。署名必須の SP は署名の無い要求を断る | `SamlEndToEndTests`（改ざん・別の鍵・署名なし） |
| SAML のアサーションの宛先のすり替え | ACS は登録された URL だけ。要求が名乗る ACS が違えば断る | `SamlEndToEndTests.登録と違う ACS…` |
| SAML のログアウトの偽造 | 証明書を登録した SP は、署名の無い要求を断る | `SamlEndToEndTests.署名の無いログアウト要求…` |
| XXE・巨大 XML（メタデータの取り込み） | DTD を禁止して先に読む。1 MB まで | `SamlEndToEndTests`、`ImportMetadataTests` |
| 署名鍵の漏えい（DB） | 秘密鍵は AES-GCM で暗号化して保存（鍵は `IDP_SECRET_KEY`） | `SigningKeyServiceTests` |
| シークレット・コード・トークンの漏えい（DB） | ハッシュ（SHA-256）だけを持つ。値は作成時に 1 度しか見せない | `AdminEndToEndTests`、`ClientSecretsTests` |
| 管理者でなくなった人の既存セッション | 管理 API は毎回 Pleasanter から引き直す | `AdminEndToEndTests` |
| DB 通信の盗聴 | 接続文字列の暗号化を起動時に検査し、切っていれば止める | `ConnectionSecurityTests` |
| Pleasanter の DB への書き込み | SQL は `SELECT` だけ。運用では読み取り専用ユーザー | `LoginEndToEndTests.Pleasanter の表へは何も書き込まない` |
| 使えないはずの人への発行（連携先ごとの Include / Exclude） | 認可・コード交換・リフレッシュ・SAML の SSO のたびに Pleasanter を引き直して判定する。Exclude が Include に勝つ | `AccessRulesTests`、`AccessRuleEndToEndTests`（OIDC・リフレッシュ・SAML） |
| 管理画面へ入れる人の権限の奪い合い・締め出し | 入れる人の条件（役割・ログイン ID・Include / Exclude）は設定ファイルか環境変数だけ。管理画面・管理 API からは変えられない。誤った指定は起動で止める | `AdminAccessRuleEndToEndTests`、`ParameterFilesTests` |
| 巨大なリクエスト | リクエスト本文は 256 KB、フォームは 64 項目・16 KB まで | `LoginEndToEndTests.巨大な要求本文は受け付けない` |

**既知の限界（ログイン ID の実在の推測）。** 応答の中身と、ダミーのハッシュ計算による時間は揃えてあるが、
存在しない ID では Pleasanter への 2 回目の問い合わせ（大文字小文字を畳んだ検索）が走るため、**厳密には時間の差が残り得る**。
総当たり側の締め出し（ID ごと・IP ごと）で緩和しているが、時間差だけで実在を断定できないことまでは保証しない。

## 2. 可用性

- `/healthz`（生存）と `/ready`（IdP 自身の DB へ繋がるか）。**`/ready` は Pleasanter の DB を見ない。**
  Pleasanter の DB が止まっても、プロセスを再起動して直るものではないため（状態は管理画面に出る）
- マイグレーションが終わるまでは、`/healthz` と `/ready` 以外は 503
- **Pleasanter の DB が止まると、サインインはできない**（既存のセッションでの SSO と、発行済みのトークンの
  検証（署名・期限）は動くが、UserInfo・トークン発行・管理 API は Pleasanter の DB を引くので失敗する）。
  Pleasanter の DB の可用性が、そのまま IdP の可用性の上限になる

## 3. 性能

- 認証 1 回あたり、Pleasanter の DB へ `Users` の 1 件取得（索引が使えれば 1 回。無ければ小文字で比べ直す）と、
  メール・部署・グループの取得。IdP の DB へ数回の読み書き
- 署名鍵は 30 秒キャッシュ。ID トークンの署名は RSA-2048
- 負荷試験は**していない**（未確認）

## 4. 国際化

画面は日本語と英語（`Accept-Language`）。サーバが描く画面（ログイン・TOTP・エラー）と、管理画面（SPA）で文言を別に持つ。
未翻訳は英語へ落とす。

## 5. ログ・監査

- 認証の成否・トークン発行・管理操作を `AuditLogs` へ残す。**失敗も残す**（試みられたことが分かる）
- **要求の本文には触れない。** パスワード・シークレット・トークン・認可コード・TOTP の数字は、
  記録できる場所自体が無い（補足は識別子と理由の符号だけ）
- 記録が失敗しても操作は通す（ログへ出す）
- ログの値は `LogSafe` で改行などを落とす（ログの偽造を防ぐ）
