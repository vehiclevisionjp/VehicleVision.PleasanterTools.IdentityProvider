# SAML 連携 運用手順書

連携先のアプリ（SP）から、この IdP を SAML 2.0 の IdP として使うための手順。
設計の要点は [`アーキテクチャ方針.md`](アーキテクチャ方針.md) の「5. SAML 2.0」。

## IdP の情報

`{Issuer}` は `IDP_ISSUER`。**管理画面のダッシュボードに、そのままコピーできる形で出る。**

| 項目 | 値 |
| --- | --- |
| メタデータ URL | `{Issuer}/saml/metadata` |
| エンティティ ID | `{Issuer}/saml/metadata`（メタデータ URL と同じ） |
| シングルサインオン URL | `{Issuer}/saml/sso`（HTTP-Redirect / HTTP-POST の両方） |
| シングルログアウト URL | `{Issuer}/saml/slo`（HTTP-Redirect / HTTP-POST の両方） |
| 署名用の証明書 | メタデータに入っている。管理画面の「署名鍵」からも PEM で取れる |
| NameID 形式 | `emailAddress` / `persistent` / `unspecified` / `transient`（SP ごとに選ぶ） |

**SP がメタデータの URL を読めるなら、それを 1 つ設定すれば足りる。** 読めない SP には、上の値を手で入れる。

## 1. SP を登録する

管理画面（`{Issuer}/admin`）の「SAML サービスプロバイダ」で作る。**SP のメタデータ XML を貼り付けると、
エンティティ ID・ACS・SLO・署名用の証明書を読み取って、下書きを作る**（保存はしない。内容を確かめて保存する）。

| 項目 | 内容 |
| --- | --- |
| エンティティ ID | SP のエンティティ ID（AuthnRequest の `Issuer` と**完全一致**） |
| ACS URL | アサーションの送り先。**要求が別の ACS を名乗っても、ここへしか送らない** |
| SLO URL | ログアウト応答の送り先（無ければ、応答は画面表示で済ませる） |
| 署名用の証明書 | SP の署名用証明書（PEM または Base64）。**署名付きの AuthnRequest / LogoutRequest の検証に使う** |
| 署名付き要求を必須にする | 署名の無い AuthnRequest を断る。**証明書の登録が要る** |
| NameID の形式・元 | 形式（上表）と、元（`loginId` / `email` / `userId` / `globalId`）。`transient` は毎回ランダム |
| 属性の対応 | SP が受け取る属性名と、元（`loginId` `email` `name` `userId` `userCode` `dept` `groups` `tenantId` `language`）。`groups` は複数値。**1 つも対応づけない（NameID だけを使う）SP には、`loginId`（ログイン ID）を 1 つだけ載せる**（ライブラリが属性の無いアサーションを書けないため） |
| 署名の対象 | アサーション・応答・両方（既定は両方）。**どちらか 1 つは署名する** |
| 許可するテナント | 空なら全テナント |

**NameID の元に `email` を選んだとき、Pleasanter にメールアドレスが無い人には応答しない**（空の NameID は出さない）。
安定した識別子が要る SP には `userId`（`persistent`）を勧める（ログイン ID やメールアドレスは変わり得る）。

## 2. SP 側の設定

| SP の項目 | 値 |
| --- | --- |
| IdP のエンティティ ID | `{Issuer}/saml/metadata` |
| IdP の SSO URL / バインディング | `{Issuer}/saml/sso` / HTTP-Redirect（または POST） |
| IdP の SLO URL | `{Issuer}/saml/slo` |
| IdP の署名用証明書 | メタデータの証明書。**SP は応答（またはアサーション）の署名を必ず検証する設定にする** |
| NameID 形式・属性 | 1 の登録と合わせる |

## 3. 動作の確認

1. SP のログインを開く → IdP のサインイン画面（パスワード。TOTP を登録済みならコードも）
2. 通ると、SP の ACS へ署名付きの応答が POST される（ブラウザが自動で送る。ボタンも出る）
3. 管理画面の「監査ログ」に `saml.response.issued` が残る。失敗は `saml.response.denied` / `saml.request.rejected`

## 4. 署名鍵とローテーション

- 署名用の鍵と証明書は初回起動で作る（自己署名・10 年）。**SP は信頼の起点を証明書そのもので持つ**ので、
  期限や CA は見ない SP が多い。見る SP には、置き換える手順が要る
- **管理画面の「署名鍵」で SAML 用をローテーションできる。** 新しい鍵で署名し始めるが、
  **旧鍵の証明書もメタデータに残る**（SP が古い証明書で検証している間も通る）。
  メタデータを定期的に読み直さない SP には、新しい証明書を SP へ登録してから旧鍵を消す
- 手順: ① ローテーション → ② 新しい証明書（管理画面からコピー）を各 SP へ登録 → ③ SP の登録が済んだことを
  確認 → ④ 退役した鍵を削除

## 5. シングルログアウト

- **SP 起点だけ。** SP が `{Issuer}/saml/slo` へ署名付きの LogoutRequest を送ると、IdP のセッションを閉じ、
  SLO URL へ LogoutResponse を返す
- **証明書を登録した SP は、署名の無いログアウト要求を受け付けない**（誰でもログアウトさせられる口にしない）。
  署名付きなら、ブラウザの cookie が無くても（SP のサーバから直接でも）、セッション索引と NameID で
  対応づけて閉じる
- **他の SP へのログアウトの伝播はしない。** 1 つの SP からログアウトしても、同じ IdP セッションで
  ログインした他の SP のセッションは、SP 側に残る

## 6. 対応しないもの

IdP 起点の SSO、Artifact バインディング、アサーションの暗号化、`NameIDPolicy` による形式の交渉
（SP ごとの登録を使う）、他の SP への SLO の伝播。

## 7. うまくいかないとき

| 症状 | 原因と対処 |
| --- | --- |
| 「要求を処理できません」（400） | エンティティ ID が登録と違う・SP が無効・署名が必須なのに無い・署名が合わない・ACS が登録と違う。IdP のログ（警告）に理由が出る |
| 署名が合わない | SP が署名に使う鍵と、登録した証明書が違う。**SP の署名アルゴリズムは RSA-SHA256 / 384 / 512 だけ受ける（SHA-1 は受けない）** |
| 「メールアドレスを必要としますが…」（403） | NameID の元が `email` で、Pleasanter にメールが無い |
| 「このアプリケーションは、あなたのテナントでは使えません」（403） | SP の「許可するテナント」に、ユーザーのテナントが無い |
| SP が応答の署名エラーにする | SP が古い証明書を持っている（ローテーション後）。新しい証明書を SP へ登録する |
| サインインできない | [`認証とTOTP-運用手順書.md`](認証とTOTP-運用手順書.md) |
