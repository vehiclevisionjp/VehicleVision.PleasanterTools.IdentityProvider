## 1. 実際の Pleasanter の DB を読む

実機の SQL Server（Pleasanter の CodeDefiner が作ったスキーマ）に対して確かめた。**手で確かめた。**

| 確認 | 結果 |
| --- | --- |
| `Users` `MailAddresses` `Depts` `Groups` `GroupMembers` の列の名前と型 | IdP が読む列は全て存在し、名前・型が一致（`INFORMATION_SCHEMA.COLUMNS`） |
| 初期管理者 `Administrator` / `pleasanter` で IdP にサインイン | 通る（`Users.Password` の SHA-512 が一致）。**ただし作成直後は `PasswordExpirationTime` が作成時刻で、そのままでは入れない**（Pleasanter の仕様どおり。Pleasanter でパスワードを変えるまでの扱い。[`認証とTOTP-運用手順書.md`](認証とTOTP-運用手順書.md)） |
| `Administrator` は `TenantManager` だけで `ServiceManager` ではない | **管理者の役割を `ServiceManager` にすると、既定の管理者は管理画面に入れない。** そのため既定の役割を `TenantManager`（テナント管理者以上）にした（検証後の変更。この実機ではこの変更の後を確かめていない） |
| メール・グループ | `MailAddresses` へ `Users` 宛てと `Groups` 宛てを入れ、IdP が `Users` 宛てだけを、登録順に返す。無効なグループは出ない |

## 2. Pleasanter が登録した TOTP をそのまま使う

**この IdP の肝。** Pleasanter 本体に TOTP を登録させ、その共有鍵で IdP のサインインが通ることを確かめた。**手で確かめた**
（Playwright。`tests/` には入れていない。Pleasanter の設定の書き換えと再起動が要るため）。

1. Pleasanter の `Security.json` の `SecondaryAuthentication` を `Mode: DefaultEnable` / `NotificationType: Totp` にして再起動
2. Pleasanter へ `Administrator` でログイン → 画面に共有鍵（`XTQO-6F2H-RG2H-XI2V-…`、Base32、4 文字ごとのハイフン）と
   コードの入力欄が出る
3. **自前で計算した 6 桁（30 秒・SHA-1）を入れると、Pleasanter が受け付けた**（= 鍵の形式・桁・周期の理解が合っている）
4. DB を見ると `SecretKey = XTQO6F2HRG2HXI2VUPH4REY5HDE3BWGZ`（ハイフンなし）、`EnableSecretKey = 1`
5. IdP でサインイン → パスワードのあとに TOTP の画面 → **誤ったコードは断られ、同じ鍵の正しいコードで通る**。
   `amr` は `["pwd","otp"]`、`acr` は `mfa`

## 3. 4 つの RDBMS

`IDP_INTEGRATION=1` で、IdP 自身の DB と、Pleasanter の `Users` などを読む実装を、SQLite・SQL Server・PostgreSQL・MySQL の
実機へ当てた（**テストに入っている**）。

- 各ストア 22 項目 × 4 RDBMS、Pleasanter の読み取り 8 項目 × 4 RDBMS、通しの E2E（OIDC・TOTP・SAML）× 4 RDBMS
- **並列に当てて 1 回しか成功しないこと**（認可コード・リフレッシュトークン・TOTP の枠・保留中の要求）を 12 並列で確認。
  失敗の数え上げが取りこぼさないこと（16 並列）も確認

PostgreSQL と MySQL では、Pleasanter 本体のスキーマではなく**同じ列名・同等の型で作った表**で確かめた
（実際の Pleasanter を PostgreSQL / MySQL で動かしての確認は未）。

## 6. 検証で見つかって直した不具合

| # | 不具合 | 見つけた方法 | 直し方 |
| --- | --- | --- | --- |
| 1 | **署名付きの SAML 要求を、証明書を渡しても検証していなかった。** 改ざんした要求も、別の鍵で署名した要求も通った | 結合テスト（改ざん・別の鍵）と、ライブラリ単体の再現 | `Saml2Configuration.SignAuthnRequest` を立てる（ライブラリはこれが無いと検証しない） |
| 2 | **`Referrer-Policy: no-referrer` だと、ブラウザは同じオリジンへのフォーム送信でも `Origin: null` を送り、CSRF の検査で全てのログインが断られた** | 実ブラウザ | `same-origin` にする |
| 3 | 管理画面の `style` 属性が CSP（`style-src 'self'`）に拒否された | 実ブラウザのコンソール | クラスへ替える |
| 4 | MySQL の表が `utf8mb3` になり、絵文字を保存できなかった | 実機（MySQL） | 初期スキーマで `utf8mb4_bin` へ変換 |
| 5 | PostgreSQL の `LIKE` が大文字小文字を区別し、絞り込みが外れた | 実機（PostgreSQL） | `LOWER` で揃える |
| 6 | 属性を 1 つも対応づけていない SAML の SP で 500（ライブラリが属性の無い `AttributeStatement` を書けない） | `node-saml` との通し | `loginId` を 1 つだけ載せる |
| 7 | スモークテストの `curl \| grep -q` が、応答の小さいリダイレクトで SIGPIPE により「ヘッダが無い」と誤判定した | 実機 | ヘッダを変数へ取ってから見る |
| 8 | 管理画面の SAML SP の新規作成で、応答への署名の既定が仕様と食い違っていた | 画面の確認 | 既定を両方署名にする |

## 7. 未確認

- **PostgreSQL / MySQL 上の本物の Pleasanter のスキーマ**（列の名前は同じ定義から作られるが、型は未確認）
- **SQL Server 以外で読み取り専用ユーザーを作る SQL**（導入手順書の PostgreSQL / MySQL の例は未検証）
- **Firefox・Safari**（Chromium だけ）、モバイル
- **本物の SP / RP 製品**（Keycloak・Azure AD・各種 SaaS など）との連携。`openid-client` と `node-saml` だけ
- **署名付きの AuthnRequest を `node-saml` から**送る経路（ITfoxtec の SP 側では通している）
- **https・HSTS を有効にした経路の通し**（検証は `IDP_ALLOW_INSECURE=true` またはループバックの http）
- **複数インスタンスを実際に並べた動作**（並列のストアの試験で代える）
- **負荷・性能**（Pleasanter の DB の `LoginId` の索引の有無を含む）
- **Azure App Service / IIS / AKS への配置**（コンテナのビルドと起動だけ確認）
- **Pleasanter 側でパスワードを変更するフローを通した後の IdP のサインイン**（`PasswordExpirationTime` を直接 `NULL` にして確認）
- **メールによる二次認証**・LDAP / 外部認証プロバイダのユーザー（対応しない）
